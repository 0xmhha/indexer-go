# 수집 성능과 지연 분석 (10/5)

## 1. 결론

`BenchmarkIngest`의 약 3초는 블록 하나의 처리 시간이 아니다. 블록 202개, 거래 10,001건을 색인하는 데 걸린 전체 시간이다. 블록당 약 16ms(블록당 거래 50건)이고, 초당 약 3,000건의 거래를 처리한다.

1초 블록 체인에서 지연을 좌우하는 것은 처리 시간이 아니라 live 루프의 폴링 대기다. 기본 설정에서는 head를 따라잡은 뒤 5초를 기다린다. 그래서 블록이 노드에 나온 뒤 색인되기까지 평균 2.4초, 최대 4.6초가 걸렸다. 대기를 200ms로 줄이면 평균 83ms, p95 183ms가 된다.

---

## 2. 측정 방법

| 측정 | 방법 |
|---|---|
| CPU 프로파일 | `BenchmarkIngest/regular/atomic`(블록 202개, 거래 10,001건)을 `-cpuprofile`로 3회 |
| 단계별 시간 | 블록 수집·해석, receipt 수집·해석, go-ethereum 보기 변환, core 쓰기, 기능 처리, undo 기록, batch commit과 fsync에 임시 타이머를 넣고 같은 부하를 색인. 측정 뒤 타이머는 지웠다 |
| head 지연 | 로컬 go-stablenet(약 1.2초 블록)에 live 루프를 30초 동안 붙였다. 별도 감시자가 20ms마다 노드 head를 읽어 블록이 처음 보인 시각을 기록하고, 커서가 그 블록에 도달한 시각과의 차이를 쟀다. `chunk_size` 100(대기 5초)과 1(대기 200ms)을 비교했다 |

측정 환경은 개발 기계 한 대다. 가짜 노드(테스트 서버)와 go-stablenet 노드 3개가 같은 기계에서 돈다. 가짜 노드의 JSON 생성 비용이 CPU 프로파일의 약 15%를 차지하는데, 운영에서는 이 비용이 노드 쪽에 있다.

## 3. 결과

### 3.1 블록 하나의 처리 시간 (거래 50건)

| 단계 | 블록당 | 비율 |
|---|---|---|
| 블록 RPC + 프로필 해석(hash·송신자 검증 포함) | 5.2ms | 32% |
| receipt RPC + 해석 | 2.7ms | 17% |
| go-ethereum 보기 변환 | 0.06ms | 0.4% |
| core 쓰기 | 0.4ms | 2% |
| 기능 처리(주소·잔액·토큰·AA·StableNet) | 0.6ms | 4% |
| undo 기록 | 1.5ms | 9% |
| batch commit + fsync | 5.6ms | 35% |
| 합계 | 16ms | |

- 처리 시간의 약 80%는 RPC 왕복과 디스크 fsync를 기다리는 시간이다. CPU 사용률은 43%였다.
- 이 단계들은 블록마다 차례대로 실행된다. 블록을 받는 동안에는 저장하지 않고, 저장하는 동안에는 다음 블록을 받지 않는다. 블록 RPC와 receipt RPC도 차례로 보낸다.
- CPU 기준으로는 undo 기록이 저장 쪽에서 가장 크다. 블록이 쓴 키마다 DB에서 이전 값을 읽기 때문이다.
- 프로필 해석은 거래마다 서명에서 송신자를 복구한다(ecrecover). 블록당 약 2.3ms, 거래당 약 46µs로 추정한다. 거래 1,000건짜리 블록이면 약 46ms가 된다.

### 3.2 head 지연

| 설정 | 표본 | 평균 | p50 | p95 | 최대 |
|---|---|---|---|---|---|
| `chunk_size` 100 (기본, 대기 5초) | 24블록 | 2.425s | 2.515s | 4.548s | 4.558s |
| `chunk_size` 1 (대기 200ms) | 29블록 | 83ms | 76ms | 183ms | 189ms |

대기 간격은 `main.go`가 정한다. `chunk_size`가 1이면 200ms, 아니면 5초다. 기본값은 100이고, 저장소의 설정 파일 세 개는 모두 5~10이다. 이 값은 RPC 오류 재시도 간격으로도 쓰인다. 200ms일 때 남는 지연(평균 83ms)도 대부분 폴링 간격의 절반(100ms 근처)과 블록 처리 시간이다.

## 4. 병목과 개선안

| 순위 | 병목 | 개선안 | 기대 효과 | 단점 |
|---|---|---|---|---|
| 1 | 폴링 대기(5초) | 폴링 간격을 재시도 간격과 분리한다(`indexer.poll_interval`, 기본 100ms 안팎). 다음 단계로 노드의 `newHeads` 구독(WebSocket)을 쓰고 폴링은 보조로 둔다(refactoring-plan C-01) | head 지연 평균 2.4초 → 약 0.1초(폴링), 구독이면 처리 시간 수준 | 폴링을 줄이면 노드 RPC 호출이 는다(100ms면 초당 10회). 구독은 WebSocket 끊김 처리가 필요하다 |
| 2 | 수집과 저장이 차례로 실행 | 다음 블록의 RPC와 해석을 지금 블록의 저장과 겹친다(파이프라인). 블록 RPC와 receipt RPC를 동시에 보낸다 | catch-up 처리량이 블록당 약 16ms에서 약 8ms로(RPC와 저장 중 큰 쪽) | 순서와 reorg 감지를 지키도록 구조가 복잡해진다. 메모리를 더 쓴다 |
| 3 | 블록마다 fsync(5.6ms) | catch-up 중에는 여러 블록을 한 번에 commit하고, head에서는 블록마다 commit한다 | catch-up 처리량 증가 | 장애 때 다시 처리할 블록이 늘어난다(멱등이라 정합성은 유지된다). head 지연에는 효과가 없다 |
| 4 | undo 기록(1.5ms) | 즉시 확정 체인(StableNet WBFT)에서는 undo를 쓰지 않는다. 프로필이 finality를 알려 준다 | StableNet에서 블록당 1.5ms 절약 | 체인 설정이 틀리면 reorg를 되돌릴 수 없다 |
| 5 | 송신자 복구(거래당 약 46µs) | 거래 서명 검증을 여러 코어에서 병렬로 한다 | 큰 블록의 해석 시간을 코어 수만큼 줄인다 | CPU 사용량이 순간적으로 늘어난다 |

1번이 head 지연의 거의 전부를 차지하므로 가장 먼저 한다. 2번은 head 지연보다 catch-up 처리량과 거래가 많은 블록에 효과가 있다. 3~5번은 측정값이 작거나 특정 상황에만 효과가 있다.

## 5. 개선 결과 (10/5)

목표: 블록이 노드에 나온 뒤 100ms 안에 색인을 마친다.

| 변경 | 내용 |
|---|---|
| 폴링 간격 분리 | `indexer.poll_interval`(기본 50ms, `INDEXER_POLL_INTERVAL`)을 오류 재시도 간격과 분리했다. head를 따라잡은 뒤에는 이 간격으로 노드에 묻는다 |
| 블록·receipt 한 번에 요청 | `Source.BlockWithReceipts`가 `eth_getBlockByNumber`와 `eth_getBlockReceipts`를 JSON-RPC batch 하나로 보낸다(왕복 2번 → 1번). receipt를 블록 단위로 주지 않는 노드에서는 거래별 조회로 넘어간다. batch 사이에 reorg가 나서 둘이 다른 블록이면 기존 receipt 검사가 걸러 낸다 |
| 거래·receipt 병렬 해석 | 32건 이상이면 거래 해석(서명 복구 포함)과 receipt 해석을 여러 코어에서 나눠 한다. 블록 해석과 receipt 해석도 동시에 실행한다 |
| undo 이전 값 병렬 읽기 | 블록이 쓴 키가 256개 이상이면 이전 값을 여러 코어에서 읽는다 |

### 5.1 head 지연 (로컬 go-stablenet, 30초)

| 설정 | 평균 | p50 | p95 | 최대 |
|---|---|---|---|---|
| 변경 전 기본(대기 5초) | 2.425s | 2.515s | 4.548s | 4.558s |
| 변경 후 기본(폴링 50ms) | 24ms | 25~26ms | 45~47ms | 47~51ms |
| 폴링 20ms | 9ms | 10ms | 21ms | 21ms |

`TestLiveHeadLatency`(`INDEXER_LIVE_RPC`와 `INDEXER_LIVE_LATENCY=1`이 있을 때만 실행)가 같은 측정을 하고 p95가 100ms 이하인지 확인한다.

### 5.2 거래가 많은 블록 하나의 처리 시간 (가짜 노드, p50)

| 블록 | 변경 전 전체 | 변경 후 전체 | 그중 노드 응답·전송 | 그중 인덱서 처리 |
|---|---|---|---|---|
| 거래 50건 | 16ms | 11ms | 5ms | 6ms |
| 거래 200건 | 43ms | 25ms | 17ms | 9ms |
| 거래 500건 | 101ms | 60~70ms | 41ms | 20~24ms |
| 거래 1000건 | 198ms | 102~105ms | 80ms | 23~27ms |

노드 응답·전송 시간은 같은 블록에 같은 batch를 보내 해석 없이 잰 값이다. 인덱서 처리는 블록마다 (전체 − 노드 응답)의 중앙값이다. 거래 1000건 블록의 해석만 따로 재면 순차 40ms가 병렬 5.7ms다(`BenchmarkDecodeTxs`).

측정한 기계에서는 Docker 가상머신과 다른 노드, 다른 시험 프로세스가 함께 돌아 부하 평균이 20~33이었다. 표의 값은 이 조건에서 잰 것이다.

### 5.3 남은 것

- 거래가 많은 블록에서는 노드가 응답을 만드는 시간이 전체를 좌우한다. 가짜 노드는 거래 1000건 블록에 약 80ms가 걸렸다. 실제 go-stablenet의 값은 재지 않았다. 부하를 주는 거래 생성기로 따로 재야 한다.
- 폴링 대기(평균 간격의 절반)를 없애려면 노드의 `newHeads` 구독을 쓴다. WebSocket 끊김 처리가 필요하다.
- 폴링 50ms는 노드에 초당 약 20번 `eth_blockNumber`를 보낸다. 노드가 여러 인덱서를 받거나 원격이면 간격을 늘리거나 구독으로 바꾼다.
