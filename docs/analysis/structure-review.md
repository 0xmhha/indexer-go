# indexer-go 구조 검토 (10/3)

> 이 문서는 nu-54v-dk-toy 저장소(NU-54V-DK 결제 프로젝트)에서 작성해 2026-10-03에 이 저장소로 옮겼다. 본문의 N25, N08 같은 번호는 그 저장소 설계 register의 결정 번호이고, P07-FR-01 같은 번호는 그 저장소 P07 indexer의 요구사항 번호다.

P07에 `indexer-go`를 쓰려다 그대로 쓰지 못한 경험에서 세 가지 문제가 제기되었다. 강결합 구조, PebbleDB 전용 저장소, 프로젝트에 맞춘 설정과 수집의 어려움이다. 이 문서는 그 세 문제를 코드로 확인하고, indexer가 갖춰야 할 기능 전체를 정리한다. 이어서 온체인 DEX처럼 실시간·대용량 트래픽을 받는 백엔드로서 `indexer-go`를 평가하고, 연산이 많은 부분을 Rust 라이브러리로 떼는 것이 맞는지 검토한다.

대상은 `stable-platform/indexer-go` 커밋 `5baff64`이다. 수치는 AST 그래프(nu-54v-dk-toy 저장소의 `products/p10-platform/tools/astgraph`)와 코드 확인에서 나왔고, 재사용 판단은 [indexer-go 재사용 분석](p07-reuse.md)에 있다.

## 1. 결론

세 문제는 모두 사실이다. 다만 원인을 정확히 짚어야 고칠 방향이 나온다.

- **강결합**은 인터페이스가 없어서 생긴 것이 아니다. 저장소에는 인터페이스가 43개 있고, 대부분의 소비자는 인터페이스에 기댄다. 문제는 세 곳에 있다.
  - 인터페이스가 PebbleDB 구현과 같은 패키지에 있다.
  - 인터페이스 묶음이 지나치게 넓다(구현체 메서드 238개).
  - 그 안에 바이트 키·값 저장(`KVStore`)과 `Compact`가 섞여 있다.
- **PebbleDB 전용**인 이유는 인터페이스를 갈아 끼울 수 없기 때문이다. 키 설계가 패키지 밖까지 새어 나가 있고(다른 4개 패키지가 자기 키를 직접 만든다), 조회 기능(범위, 필터, 페이지)이 Pebble 반복자 위에 손으로 짜여 있다.
- **프로젝트 맞춤 수집이 어려운 것**은 설계 전제 때문이다. `indexer-go`는 "체인 전체를 색인하는 탐색기"를 전제로 한다. 수집 대상을 선언하는 설정(컨트랙트, 이벤트, 도메인 테이블)과 사용자 정의 처리기 연결점이 없다.

실시간·대용량 서비스 백엔드로서는 지금 구조가 맞지 않는다. 결정적인 원인은 다섯 가지다.
- 임베디드 단일 writer DB에 API가 같은 프로세스로 붙어 있어 읽기를 수평 확장할 수 없다. 설정의 읽기 전용 모드도 실제로는 쓰이지 않는다.
- 조회가 "전부 읽어서 메모리에서 거르고 자르는" 방식이다.
- 이벤트 전달이 구독자 전체를 선형으로 훑는다.
- 키가 문자열 포맷팅으로 만들어진다.
- reorg를 감지하지 못한다.

Rust 추출은 지금 단계에서 권장하지 않는다. indexer의 병목은 I/O와 데이터 구조이고, 남은 연산(keccak, secp256k1, BLS)은 이미 C나 어셈블리로 최적화된 구현을 쓴다. DEX의 경로 탐색이나 대량 시뮬레이션처럼 연산 밀도가 높은 독립 기능이 생기면, 그때 별도 서비스로 검토한다(5절).

## 2. 제기된 세 문제의 확인

### 문제 1: 구조와 모듈화가 계층화되지 않아 강결합이다

AST 그래프로 본 사실은 다음과 같다.

| 확인한 것 | 수치 | 뜻 |
|---|---|---|
| `pkg/storage`를 import하는 패키지 | 13개(전체 42개 중) | 저장소가 허브다 |
| `pkg/storage` 자체 크기 | 17,152줄, 파일 중 19개가 PebbleDB를 import | 인터페이스와 구현이 한 패키지에 있다 |
| 저장소 인터페이스 | 43개(`Reader`, `LogReader`, `UserOpIndexReader` 등) | 소비자는 대부분 좁은 인터페이스에 기댄다(좋은 점) |
| `Storage` 인터페이스 | 22개 인터페이스를 묶고 `KVStore`, `NewBatch`, `Compact([]byte, []byte)`를 더한 것 | 구현체 하나(`PebbleStorage`)가 메서드 238개를 가진다 |
| 구체 타입 의존 | `pkg/api/graphql`이 `s.storage.(*storage.PebbleStorage)` 타입 단언 5곳, `cmd/indexer` 1곳 | 인터페이스를 우회해 Pebble 구현에 붙는다 |
| 수집기 하나를 떼어 낼 때 딸려 오는 것 | gap 복구만 5,997줄(fetch, events, storage, userop) | 기능 단위 분리가 안 된다 |
| 가장 큰 함수·파일 | GraphQL 타입 정의 함수 910줄, `types.go` 2,939줄 | API 층이 거대한 단일 파일들이다 |

판단은 다음과 같다. "인터페이스를 썼다"와 "계층이 분리되었다"는 다르다. 포트(인터페이스)가 어댑터(Pebble 구현)와 같은 패키지에 있으므로, 인터페이스만 쓰려 해도 Pebble을 import하게 된다. 또 `Storage`가 모든 기능의 합집합이라 새 저장소를 붙이려면 238개 메서드를 다 구현해야 한다. 그 결과 기능(수집, 디코딩, 도메인 처리, 저장, API)을 따로 쓸 수 없고 통째로만 쓸 수 있다.

### 문제 2: PebbleDB만 지원해 PostgreSQL 같은 다른 DB를 쓸 수 없다

| 확인한 것 | 근거 |
|---|---|
| 저장소 구현이 하나뿐이다 | `NewPebbleStorage` 외 구현이 없다 |
| 키 설계가 밖으로 새어 나간다 | `pkg/notifications`, `pkg/resilience`, `pkg/watchlist`, `cmd/indexer`가 `KVStore.Put/Iterate`로 자기 키를 직접 쓴다(40여 곳). SQL 저장소라면 이들을 위해 KV 흉내를 내야 한다 |
| 조회 기능이 반복자 위에 손으로 짜여 있다 | `GetLogs`: 주소 또는 첫 topic 하나로만 색인 범위를 읽고, 나머지 topic과 주소는 메모리에서 거른다. 최대 10,000블록이다 |
| 키가 문자열 포맷팅이다 | `fmt.Sprintf("%s%020d/%06d/%06d", ...)`로 쓰고 `fmt.Sscanf`로 읽는다 |
| 정렬이 깨지는 키가 있다 | `BlockKey`, `TransactionKey`는 자리 채움 없는 `%d`라 사전순이 숫자순과 다르다("10" < "9"). 범위 함수 `BlockKeyRange`는 지금 쓰이지 않아 실제 오류는 나지 않지만, 쓰는 순간 잘못된 범위를 읽는다 |

판단: DB를 바꾸는 일은 어댑터 하나를 추가하는 수준이 아니라 저장 계층 재설계다. PostgreSQL에서는 범위·필터·페이지·집계를 SQL과 인덱스가 맡아야 하는데, 지금은 그 논리가 Pebble 반복자 코드 안에 흩어져 있다.

### 문제 3: 프로젝트에 바로 쓸 수 없어 다시 만들게 되고, 설정과 프로젝트 전용 수집이 불편하다

| 확인한 것 | 근거 |
|---|---|
| 수집 범위를 정하는 설정이 없다 | 설정 항목은 `rpc`, `database`, `storage`, `log`, `indexer`, `api`, `verifier`뿐이다. 특정 컨트랙트·이벤트만 수집하는 선언이 없다. `start_height`와 `address_indexing` 정도만 있다 |
| 처리 단위가 블록 전체다 | Fetcher는 블록마다 블록과 receipt를 모두 가져와 처리한다. P07처럼 이벤트 하나만 필요해도 체인 전체를 받는다 |
| 사용자 정의 처리기 연결점이 없다 | 4337, 7702, 토큰, 시스템 컨트랙트 같은 처리기는 코드에 박혀 있다. "이 이벤트가 오면 이 도메인 테이블을 갱신"을 끼워 넣을 공개 연결점이 없다. 컨트랙트 등록(ABI)은 decode만 한다 |
| 읽기 전용 설정이 무시된다 | `database.readonly`(`INDEXER_DB_READONLY`)를 읽지만, 시작 코드가 저장소를 항상 `ReadOnly = false`로 연다. API만 따로 띄울 수 없다 |
| 쓰지 않는 의존이 있다 | go.mod에 `gqlgen`이 있지만 코드가 import하지 않는다. GraphQL은 `graphql-go`로 만든다 |

판단: 맞다. `indexer-go`는 "체인 탐색기"이지 "프로젝트별 데이터 파이프라인을 만드는 프레임워크"가 아니다. 그래서 P07처럼 특정 도메인 데이터(영수증, 매출, 정산)가 필요하면 다시 만들게 된다.

### 나의 의견

`indexer-go`는 탐색기 백엔드로는 기능이 풍부하다. 4337, 7702, WBFT 합의, 컨트랙트 검증, 구독, Kafka·Redis 이벤트 버스까지 있다. 문제는 그 기능들이 하나의 저장 구현과 하나의 실행 파일에 묶여 있다는 것이다. 고칠 방향은 "더 많은 기능"이 아니라 "분해"라고 본다.

1. **포트와 어댑터 분리.** 저장소 인터페이스를 기능별 소패키지(예: `store/logs`, `store/blocks`)로 옮긴다. Pebble 구현은 `store/pebble`, PostgreSQL 구현은 `store/postgres` 어댑터로 둔다. `KVStore`는 공개 인터페이스에서 빼고 어댑터 내부로 숨긴다. 타입 단언을 없앤다.
2. **처리기(handler) 모델.** "원천 수집(블록·로그) → 디코딩 → 도메인 처리기 → 도메인 저장" 파이프라인으로 나눈다. 처리기는 설정이나 코드 등록으로 끼운다. 그러면 P07은 `PaymentSettled` 처리기와 receipts 테이블만 쓰면 되고, 탐색기는 지금의 처리기 묶음을 쓰면 된다.
3. **선언형 설정.** 수집 대상(체인, 컨트랙트 주소, ABI, 이벤트, 시작 블록, finality 정책)을 YAML로 선언한다. 하지 않을 일(블록 전체 색인 끄기)도 선언할 수 있어야 한다.
4. **실행 역할 분리.** 같은 바이너리라도 `ingest`(단일 writer)와 `api`(여러 개, 읽기 전용 또는 다른 DB 복제본 읽기)를 따로 띄울 수 있게 한다.

이 넷은 서로 이어져 있어 한 번에 하지 않아도 된다. 1번이 나머지의 전제다.

## 3. indexer가 갖춰야 할 기능

블록체인 데이터를 모아 제공하는 역할 기준으로 나열하고, `indexer-go`가 지금 가진 것을 함께 적었다(코드 검색 기준).

| 영역 | 기능 | indexer-go |
|---|---|---|
| 수집 | 블록, 트랜잭션, receipt, 로그 | 있음 |
| | 내부 호출(trace) | 있음(`debug_trace` 관련 15파일) |
| | 대기 트랜잭션(mempool) 구독 | 있음(`SubscribePendingTransactions`) |
| | 상태 변화(잔액 스냅샷, storage diff) | 잔액 스냅샷 있음, storage diff 없음 |
| | 합의·검증자 데이터 | 있음(WBFT) |
| 정합성 | finality 정책(확정 블록만 또는 n confirmation) | 없음(latest를 폴링) |
| | reorg 감지와 되돌리기 | **없음**(`DeleteBlock`만 있고 감지 루프가 없다). WBFT 즉시 확정 체인에서는 문제가 없지만 다른 EVM 체인에서는 틀린 데이터가 남는다 |
| | gap 감지와 backfill | 있음 |
| | 지정 블록부터 재색인 | 있음(reindex) |
| | 멱등 저장과 커서 | 있음(블록 단위) |
| | 처리 결과의 정확히 한 번 전달(저장과 이벤트 발행의 원자성) | 없음(저장 뒤 별도 발행) |
| 디코딩·도메인 | ABI 등록과 이벤트·함수 decode | 있음 |
| | 토큰 표준(ERC-20, 721, 1155), 보유자 | 있음 |
| | 프록시 컨트랙트 인식(EIP-1967) | 없음 |
| | 사용자 정의 도메인 처리기와 도메인 테이블(projection) | **없음** |
| 저장 | 저장소 추상화(KV, SQL, 컬럼형) | **Pebble만** |
| | 시계열 집계(OHLCV, 일·주·월 합계) | 없음 |
| | 보존 정책·pruning, 스냅샷·백업 | 일부(pruning 관련 코드 5파일) |
| 제공 | 조회 API(GraphQL, JSON-RPC 호환, Etherscan 호환) | 있음 |
| | 커서 기반 페이지 | 겉모양만 있음(`pageInfo`). 실제로는 전부 읽은 뒤 offset으로 자른다 |
| | 실시간 구독(snapshot + delta + sequence 번호) | 구독은 있으나 sequence 기반 재동기화는 없음(최근 n건 replay만) |
| | webhook과 외부 스트림(Kafka 등) | 있음 |
| 운영 | 선언형 수집 설정 | **없음** |
| | RPC 여러 개 사이 failover, RPC 속도 제한 | failover 없음 |
| | 지표, 로그, 분산 추적 | 지표·로그 있음, 추적은 미미함 |
| | ingest와 API의 분리, API 수평 확장 | **없음**(읽기 전용 설정 무시) |
| | 인증, 쿼터, 캐시 | API 키·속도 제한 있음. 응답 캐시는 RPC 프록시에만 있음 |
| | 멀티체인 | 있음 |

## 4. 실시간·대용량 백엔드로서의 평가 (DEX 기준)

### 4.1 DEX가 요구하는 것

온체인 DEX 프런트엔드와 사용자는 다음을 지연 없이 받아야 한다.
- 체결(trade) 스트림.
- 호가(L2 깊이)와 그 변화분.
- 매수·매도 잔량.
- 캔들(OHLCV).
- 사용자별 주문·체결·잔고.
- 화면에서 가공할 원천 이벤트.

이를 위한 요구는 다섯 가지다.
- **쓰기 쪽:** 블록 하나에 이벤트가 많이 몰려도 수 ms 안에 도메인 상태(호가창, 잔량)를 갱신한다.
- **읽기 쪽:** 같은 데이터를 수많은 구독자에게 보낸다. 시장별로 나눠 보내고, 느린 구독자가 전체를 막지 않아야 한다.
- **재동기화:** snapshot에 sequence 번호를 붙이고 delta를 이어 보내, 끊긴 클라이언트가 빠진 구간만 다시 받는다.
- **수평 확장:** ingest는 하나, 읽기·push 노드는 여러 개다. 노드 사이는 메시지 버스로 잇는다.
- **정합성:** latest 기준으로 보여 주므로 reorg 때 delta를 되돌리는 규칙이 필요하다.

### 4.2 지금 구조와 패턴의 평가

| 관점 | 지금 indexer-go | DEX 기준 평가 | 개선 방향 |
|---|---|---|---|
| 배포 구조 | 임베디드 Pebble 하나에 ingest와 API가 한 프로세스 | [치명] 읽기를 수평 확장할 수 없다. 읽기 전용 설정도 무시된다 | ingest(단일 writer)와 API(N개)를 분리한다. 읽기는 복제 가능한 저장소(PostgreSQL 복제본, 또는 메시지 버스로 만든 노드별 메모리 상태)에서 한다 |
| 도메인 상태 | 원천 데이터(블록, 로그) 중심. 호가창 같은 도메인 상태가 없다 | [치명] 요청마다 원천 로그에서 계산하게 된다 | 이벤트 처리기가 도메인 상태(시장별 호가창, 잔량, 캔들)를 미리 계산해 둔다(materialized view). 호가창은 가격 단위로 정렬된 구조(B-tree, 정렬 배열 + 맵)에 둔다 |
| 조회 | `GetLogs`는 색인 하나로 읽고 나머지를 메모리에서 거른다. 페이지는 전부 읽은 뒤 offset으로 자른다 | [중요] 결과 크기에 비례하는 시간과 메모리가 든다. 깊은 페이지일수록 느리다 | 조건마다 맞는 복합 색인을 두고, keyset(커서) 페이지로 바꾼다. 색인 순서 그대로 필요한 만큼만 읽는다 |
| 키·직렬화 | `fmt.Sprintf`/`Sscanf` 문자열 키, 일부는 자리 채움 없는 숫자, 값은 JSON과 RLP 혼용 | [중요] 할당과 파싱 비용이 크다. 자리 채움 없는 키는 범위 조회를 막는다 | 고정 길이 big-endian 이진 키를 쓰고, 값은 한 가지 이진 형식으로 통일한다 |
| 이벤트 전달 | `EventBus`가 이벤트마다 구독자 전체를 RLock 아래에서 선형으로 훑는다. 구독자마다 필터와 시간 측정(`time.Now`)을 하고, 버퍼가 차면 버린다 | [중요] 비용이 이벤트 수 × 구독자 수다. 버려진 이벤트를 복구할 sequence가 없다 | 주제(시장, 주소)별 구독 색인으로 라우팅하고, 구독자별 링 버퍼를 둔다. sequence와 snapshot으로 재동기화하고, 느린 구독자는 끊고 snapshot부터 다시 받게 한다. 직렬화는 구독자마다 하지 않고 한 번만 한다 |
| API | GraphQL(`graphql-go`, 리플렉션 기반)과 거대한 단일 파일들. 타입 정의 함수 하나가 910줄 | [권장] 고빈도 조회에서 GraphQL 해석 비용과 N+1이 문제가 된다 | 고빈도 경로(호가, 체결)는 WebSocket 이진·JSON 스트림과 단순 REST로 뺀다. GraphQL은 탐색 조회에만 쓴다. 스키마는 코드 생성 방식으로 나눈다 |
| 수집 방식 | latest를 폴링하고 `time.Sleep`으로 기다린다. 블록 단위 worker pool과 적응형 배치 크기 조정 | [권장] 폴링 주기만큼 지연이 생긴다. worker pool과 적응형 조정은 좋은 점이다 | `newHeads` 구독 + 폴링 보조. 블록 안의 처리 순서를 보장한다 |
| 재시도 | 지수 backoff(블록 fetch) | 좋음 | RPC 여러 개 사이 failover를 더한다 |
| reorg | 감지 없음 | [치명, 다른 체인에서] DEX는 latest를 보여 주므로 reorg 때 잘못된 체결과 호가가 남는다. StableNet(WBFT 즉시 확정)에서는 해당하지 않는다 | 블록 hash 사슬을 확인하고, 되돌릴 때 delta를 역으로 적용한다(보상 이벤트) |
| 외부 이벤트 버스 | Kafka, Redis 어댑터 있음 | 좋은 점. 노드 사이 fan-out에 쓸 수 있다 | 저장과 발행을 transactional outbox로 원자화한다 |

### 4.3 요약 판단

`indexer-go`의 수집 쪽 패턴(worker pool, 적응형 배치, backoff, gap 복구)은 쓸 만하다. 반면 제공 쪽(저장 모델, 조회, 전달, 배포 구조)은 탐색기 수준의 부하를 전제로 만들어졌다. DEX 수준의 실시간·대용량에는 이 둘을 분리한 새 구조가 필요하다. 원천 수집은 공용으로 두고, 도메인 처리기가 상태를 만들고, 전달 노드가 수평 확장되는 구조다.

## 5. Rust 라이브러리 추출 검토

### 5.1 후보와 판단

| 후보 | 지금 구현 | Rust로 떼면 얻는 것 | 판단 |
|---|---|---|---|
| keccak, RLP, ABI decode | go-ethereum(keccak은 어셈블리) | 작다. 호출 단위가 작아 cgo 호출 비용(호출당 수십~백 ns와 메모리 복사)이 이득을 넘기 쉽다 | 하지 않는다 |
| 서명 복원(secp256k1) | go-ethereum의 C 구현(libsecp256k1) | 거의 없다. 이미 C다 | 하지 않는다 |
| BLS 검증(WBFT) | `blst`(C와 어셈블리) | 없다 | 하지 않는다 |
| 이벤트 필터·라우팅, 호가창 유지 | Go 맵·슬라이스와 선형 탐색 | 언어보다 자료구조의 문제다. Go로 색인 라우팅과 정렬 구조를 쓰면 충분하다 | 하지 않는다. 자료구조부터 고친다 |
| JSON 직렬화 | `encoding/json`(리플렉션) | 효과는 있으나 Go 안에서도 코드 생성 직렬화나 이진 형식으로 같은 효과를 낸다 | Go 안에서 해결한다 |
| DEX 경로 탐색, 대량 가격 시뮬레이션, 청산·위험 계산 | 없음 | 큼. 연산 밀도가 높고, 배치 단위로 크게 호출할 수 있다 | 기능이 생기면 검토한다. 이때도 cgo 라이브러리보다 별도 서비스(gRPC)나 배치 작업을 권장한다 |

### 5.2 판단 근거와 단점

indexer의 시간은 대부분 RPC 왕복, 저장소 I/O, 직렬화, 잠금 경합에 쓰인다. 이 영역은 언어를 바꿔서가 아니라 구조(색인, 페이지, 라우팅, 수평 확장)를 바꿔서 줄어든다. 연산이 많은 암호 부분은 이미 C와 어셈블리 구현을 쓴다.

Rust 라이브러리를 cgo로 붙이면 비용이 셋 든다.
- 빌드: 교차 컴파일, 정적 링크, 두 언어의 툴체인이 필요하다.
- 운영: 메모리 소유권 경계, panic 전파, 프로파일링 단절이 생긴다.
- 조직: 두 언어의 숙련이 필요하다.

반대로 별도 서비스로 두면 경계가 네트워크라서 위 비용이 줄지만, 호출 지연이 생긴다. 그래서 큰 배치로 부르는 기능(경로 탐색, 시뮬레이션)에만 맞다.

## 6. 권장

1. **P07은 지금 구현을 유지한다**([재사용 분석](p07-reuse.md)).
   - 이번 사이클은 영수증 하나가 목적이므로 위 구조 개편을 기다리지 않는다.
   - 단점: 두 indexer 코드베이스가 당분간 따로 간다.
2. **indexer-go를 계속 키울 계획이면 2절의 분해를 먼저 한다.** 순서는 포트·어댑터 분리 → 처리기 모델 → 선언형 설정 → ingest·API 분리다.
   - 이 순서를 따르면 PostgreSQL 어댑터와 P07 같은 프로젝트 전용 수집을 "설정과 처리기 하나"로 붙일 수 있다.
   - 단점: 저장 계층과 API의 상당 부분을 다시 쓰는 큰 작업이고, 그 동안 탐색기 기능 개발이 멈춘다.
3. **DEX 같은 실시간 서비스는 indexer-go를 확장하기보다 원천 수집만 공유한다.** 도메인 처리기, 상태 저장, 전달 노드는 그 서비스의 요구(시장별 sequence, snapshot·delta, 수평 확장)에 맞춰 설계한다.
   - 단점: 수집과 서비스 사이의 계약(원천 이벤트 형식과 순서 보장)을 따로 정하고 지켜야 한다.

## 7. 한계

- 정적 분석과 코드 읽기에 근거했다. 부하 시험이나 프로파일링은 하지 않았다. 4절의 "비용이 크다"는 판단은 알고리즘 복잡도와 할당 패턴에서 추론한 것이다.
- 기능 유무(3절)는 코드 검색 기준이다. 이름이 다른 구현이 있을 수 있다.
- `indexer-go`를 testnet에 띄워 보지 않았다.
