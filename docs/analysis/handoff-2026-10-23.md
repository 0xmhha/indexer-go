## 2. 목적 (흔들리지 않게)

사용자가 직접 말한 의도다. 설계 판단은 모두 이 문단에 맞춘다.

- **PostgreSQL에 쌓는 이유는 이력이다.** 최신 상태만 필요하면 RPC로 충분하다. 운영에서는 이런 것을 찾는다. 어느 날짜, 어느 블록 높이, 어느 계정 주소의 정보. 블록 구간 사이의 자금 이동. 정상 행위와 인위적인 행위의 구분. 그래서 컬럼마다 변화를 누적하고, 최신 값 표를 따로 둔다(결정 기록 43회차).
- **상태는 거래가 만든다.** genesis가 최초 상태를 만들고, 그 뒤로는 거래가 상태를 바꾼다. 거래가 아닌 변화는 블록 보상이다. StableNet에서는 WBFT `Finalize`의 base fee 분배와 system contract 전이가 여기에 해당한다. 그래서 상태 변화는 거래별로 기록하고, 블록 단위 변화는 따로 표시한다.
- **실행부는 정상 peer다.** 다른 노드에게는 정상 peer로 보여야 하고, 블록을 전파받는다. go-stablenet을 고치지 않고 import한다. go-stablenet 전체가 아니라 peer, 검증, 실행에 필요한 부분만 쓴다.
- **실행부는 PostgreSQL에 접근하지 않는다.** PostgreSQL 쓰기는 indexer 내부 기능이 맡는다. 테이블마다 담당 writer가 자기 표만 쓴다.
- **저장소를 두 벌로 쓰지 않는다.** 노드 DB는 필요한 만큼만 두고 계속 지운다. 지우는 일은 이 프로젝트의 코드가 맡는다(E3).
- **다른 indexer보다 빨라야 한다.** E1의 속도 목표는 같은 testnet 블록에서 기존 RPC 수집보다 "블록 생성 → API 노출"의 p50과 p99가 둘 다 작은 것이다.

## 3. E1 구조 요약

```
StableNet peers ─ eth/68 NewBlock
  ▼
실행부 x/stablenet/executor (자기 go.mod, go-stablenet replace, PostgreSQL 접근 없음)
  go-stablenet eth.New + node.New ─ WBFT 검증 ─ 실행 ─ 노드 DB(path 방식)
  exporter: ChainHeadEvent로 깨어나 canonical 높이를 차례로 걸음
    블록 다시 실행(감싼 state.Database, 거래마다 IntermediateRoot)
    → 거래별 변화 + Finalize 변화, 마지막 root = header 확인
    → 실행부 로컬 spool → IPC(execwire)
  ▼
indexer
  receiver → assembler → 표별 queue와 writer 7개
    blocks / transactions / receipts / logs
    accounts(state_account_changes + state_accounts)
    storage(state_storage_changes + state_storage)
    contracts(state_contracts + state_code)
  + 기존 기능 writer(주소 색인, 토큰, AA …; 핵심 표는 쓰지 않음)
  watermark: visible_height = min(cursor) → 모든 읽기와 이벤트를 이 높이로 막음
```

자세한 것은 설계 2판의 3장~7장이다. 결정 하나하나는 decision.md 3장의 표에 있다.

**바뀐 결정에 주의한다.** 대화 중에 사용자가 의도를 고쳐 준 곳이 많다. 이전 문서의 내용과 다르면 decision.md가 정본이다.
- 처음 D2~D4는 "indexer가 header를 보내고 실행부가 PostgreSQL을 읽는다"였다. 13회차에 노드 DB를 유지하기로 바뀌었다.
- D12와 D13은 31회차에 "실행부는 PostgreSQL에 접근하지 않는다"로 바뀌었다.
- 상태 변화 추출은 D1(trie 비교)에서 D19(감싼 `state.Database`)로 바뀌었다. trie 비교는 시험에서 대조하는 용도로만 남았다.

## 4. 다음 작업

### 4.1 바로 할 일: E1 계획(03-plan)

`codemine:design-first`의 plan 단계다. 설계를 시나리오 하나가 끝까지 동작하는 작은 단위로 나눈다. 단위마다 다음을 `03-plan.md`에 적고, 사용자 검토를 받은 뒤 멈춘다.
- 영향을 받는 파일과 소비자
- 계약
- 시험
- **위험**: 무엇이 잘못될 수 있고 언제 알게 되는가
- 롤백

맨 앞에 둘 단위는 설계 11장의 미확인 항목을 확인하는 시험이다. 결과에 따라 설계가 바뀔 수 있기 때문이다.

1. **감싼 `state.Database` 검증.** E0 구간(11,492,486부터 300블록, 거래 블록 62개)에서 감싼 `state.Database`로 다시 실행한다. 모든 블록에서 root가 header와 같은지 본다. fee delegation 블록, NativeManager 거래, 슬롯을 0으로 만드는 블록을 포함한다. 거래별 root 계산 비용도 잰다.
   - 실패하면 D19를 사용자에게 다시 묻는다. 대안은 decision.md에 기록한 D19의 B와 C다.
2. **receipt 필드 비교.** `TestBinaryMatchesLiveJSON`이 허용하는 RPC JSON 경로와 binary 경로의 receipt 필드 차이를 확인한다.
   - 차이가 있으면 완료 기준 1의 "0건 차이"를 어떻게 볼지 사용자에게 묻는다.
3. **기능 핸들러의 핵심 표 의존.** 기능 핸들러가 블록 트랜잭션 안에서 `blocks`, `transactions`, `receipts`, `logs`를 다시 읽는지 코드 그래프로 찾는다.
4. **바깥 trie 노드로 노드 시작(D18).** go-stablenet 노드 DB에 바깥에서 받은 trie 노드를 넣고, 부모 블록에서 시작할 수 있는지 확인한다.
5. **되감기 깊이.** pathdb에서 `SetHead`로 얼마나 깊게 되감을 수 있는지 확인한다.

그다음 단위의 순서는 데이터 흐름을 따른다.
- execwire
- 실행부 노드 조립
- exporter와 spool
- indexer receiver와 assembler
- migration 0014와 상태 writer
- 핵심 표 writer
- watermark와 조회 필터
- 기능 writer 분리
- 되돌리기
- 시험 기반: 녹화 구간 녹화 도구(D18), 로컬 체인

## 7. 함정

- **main 브랜치 hook.** 세션의 hook이 main에서 커밋하는 것을 막는다. 같은 명령 안에서 `checkout -b`를 해도 막힌다. 브랜치를 먼저 따로 만든다.
- **macOS에는 `timeout` 명령이 없다.**
- **study 저장소 히스토리 검사.** `betterleaks git .`이 히스토리에서 `generic-api-key` 1,462건을 찾는다(대부분 `projects/wbft`). 사용자가 "히스토리에 남은 것은 무시해도 된다"고 했다. staged 검사는 계속 필수다.
- **study 저장소 checkout은 다른 세션이 함께 쓴다.** main을 맞출 때는 checkout하지 말고 `git fetch origin main:main`으로 ref만 옮긴다.
- **study 저장소에는 CI가 없다.** PR checks가 비어 있다. 로컬 `python3 plugins/<plugin>/tests/run_tests.py`로 확인한다.
- **설치된 플러그인 갱신.** `claude plugin marketplace update 0xmhha-devkit` 다음 `claude plugin update dotclaude@0xmhha-devkit`를 실행한다. marketplace가 로컬 디렉터리라 study 저장소의 지금 checkout 내용을 가져간다.
- **codemine `workflow.json`.** 승인된 gate의 decision은 `{source:"user", recorded_at, summary}` 형식이어야 검사를 통과한다.
- **결정 스크립트의 연속 횟수.** 0.3.0에서는 답을 기록할 때마다 연속 횟수가 0으로 돌아가는 잘못이 있었다. 0.3.1에서 고쳤다.
- **CI의 간헐 실패.** #208은 문서만 바꿨는데 postgres job에서 `TestManagedStateProjectionRestartAPIAndReorg`가 실패했다(`pkg/app/state_projection_test.go:134`). reorg 뒤 상태 worker의 epoch와 완료 hash를 기다리는 `require.Eventually`가 제한 시간 안에 참이 되지 않았다. 최근 CI 이력에서는 이번 한 번뿐이고, 실패한 job만 다시 돌렸다. 원인은 조사하지 않았다. 다시 나오면 대기 시간과 worker 진행 조건을 조사한다.
- **go-stablenet과 indexer는 한 바이너리에 넣을 수 없다**(work log 3.109). pebble 버전과 go-ethereum API가 충돌한다. 실행부 코드는 indexer 패키지를 import하지 않는다. 공유하는 것은 `execwire`(표준 라이브러리만 쓰는 별도 모듈)뿐이다.
