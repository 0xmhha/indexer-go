## Native implementation decisions

Use the pinned provider's typed RocksDB history table iterators/codecs, WAL-synced batches and `flush_and_compact`, without changing upstream code or DB formats. Trim each shard's lower prefix in bounded batches rather than accumulating every shard for an account. Validate nonempty lists, the native 2,000-entry shard bound, strictly separated block ranges, finite upper keys and final sentinel layout; retain unchanged suffix keys. Commit at most64 row mutations per batch. A corrupt layout aborts the candidate. Postchecks require no index entries below cutoff and exact account/storage native checkpoints. Other RocksDB tables are not logically pruned; native compaction may rewrite their physical files.

The sealed native floor moves to version2 with an exact history floor; old version1 payload-only floors remain inspectable/validatable. Old binaries fail closed on the new field/version. Checkpoint targets, seed starts and replay parents must be at/above the maximum native history checkpoint plus one. Header-only canonical diagnostics remain available. Current node/DB/source anchors and visible heights do not move.

The nonempty owned fixture creates A at1, changes it at2/3/4, deletes it at5 and recreates it at130; B is created at1 and deleted at2. At cutoff3 A has slot1=0 and slot2=9, at4 slot1=13, after5 A is absent, and after130 slot1=17 with slot2=0. Complete native roots, direct account/storage reads, seed re-export and consecutive cutoff3→4 retention must agree after reopening. Blocks are synthetic storage-library fixtures, not consensus-valid peer data.

Native boundary experiment: pruning through3 caused `insufficient changesets to revert to block #3; available4..132` in the pinned trie overlay before publication. Retain the one-block guard and test the observed boundary instead of bypassing native root validation or modifying upstream.
